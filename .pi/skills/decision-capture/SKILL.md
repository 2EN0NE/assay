# 决策捕获

把用户的决策变成**可结算的预测**。核心不是"记录一个想法"，而是把隐含信念**显性化**为概率、期限与判据。

## 为什么要做

用户不会主动量化自己的信念——这是本系统存在的理由。所以看到决策就捕获，不要等指令。

## 流程

### 1. 识别

出现下列形态即为决策：在信息不完整时对有限资源（时间、金钱、注意力、健康）做分配，且结局部分由运气决定。

- "我在纠结要不要接这个 offer"
- "我打算这季度把预算压到 X"
- "我准备赌一把，先把团队扩到 5 人"

### 2. 拆解

把决策拆成 0..n 条**可预估**命题。拆不出来的部分不硬拆——不是每个决策都有可量化子命题。

好的命题要满足：**有一个能判真伪的判据**，且**有明确的结算期限**。

### 3. 追问（追问到底，但允许"还没想清楚"）

对每一条命题，先问三件事：

| 缺口 | 问法                         |
| ---- | ---------------------------- |
| 概率 | "你有几成把握？给个数。"     |
| 期限 | "什么时候能知道结果？"       |
| 判据 | "出现什么算成、什么算不成？" |

**当事人给不出数字时，不要就此放弃，也不要替他编。** 换下面三种技巧把信念显性化——它们都只是**换一种表示**，不产生新的量：

| 技巧         | 怎么问                                                                      | 能否直接落库                                                                                                       |
| ------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **量表替代** | "那如果满分 10 分，你认为**这件事发生**的把握是几分？为什么不是更高/更低？" | **能**——刻度上的点等价于一个概率                                                                                   |
| **否定检验** | 就逻辑否定再问一次："那**不会发生**的把握是几成？" 两数之和应当为 1         | **不能**——只做一致性校验。有矛盾时问"哪个才是你真实的把握"，不要自己挑一个                                         |
| **具体化**   | "把这个概率做成转盘，有 xx% 的区域你转到就能得到 xxx，你愿意吗？"           | **不能**——赌局同时量到风险偏好与赌注大小（"愿意在 65% 下注"≠"相信 65%"），必须复述确认："所以你的把握大约在 65%？" |

判据是**换算是否无损**：同一信念换个表示（量表、刻度）可直接成为 `Forecast`；需要额外假设（如"风险中性"）的，必须经当事人复述确认。**否定检验里的否定必须是逻辑否定**，"天晴"不能替代"不下雨"——雨 30% 与晴 10% 可以由阴天补齐，凭不存在的矛盾追问，只会逼出敷衍数字。

回答的**精度本身就是信息**：说不出精确值就用粗刻度；真的说出 91.24% 往往意味着背后有成体系的分析。两者都要落库为概率，不要因为"太粗"或"太精确"而拒绝或改写。

**关键约束**：追问到底 **≠ 逼出一个数字**。"我确实想不清楚"是**合法终点**。此时**不要编造概率**，直接创建一条**未量化**的命题（省略 `--probability`）。

为什么这条约束不能省：在压力下随口给出的概率是 `Compliance Number`——它会污染校准，因为它既不是你的真实信念，又通不过"我当时真这么想吗"的复核。**未量化会被记录下来并保持可见，这是刻意的**：让"我当初逃避了量化"这件事可见，逃避才有可能被矫正。

### 4. 写入

用 CLI 落库（不要直接写数据库）：

```bash
npm run --silent agent -- create-prediction \
  --title "会在 6 月底前收到正式 offer" \
  --resolve-by 2026-06-30 \
  --criteria "邮件中出现正式 offer 字样" \
  --oracle-kind PUBLIC_FACT \
  --probability 0.7
```

- `--probability` 省略 = 未量化（合法）
- `--oracle-kind`：
  - `PUBLIC_FACT`（默认）——任何人可查证的公共事实
  - `AGENT_OBSERVABLE`——你（agent）能观测到的信号
  - `SELF_REPORT`——只能由当事人本人报告（**必须**同时给 `--anchor` 评分锚点）
- 写入的记录来源标为 agent、**默认未背书**：在当事人背书之前不计入校准。这是设计，不是缺陷。

## 输出

写入后，用一句话告诉用户：命题是什么、概率多少（或"尚未量化"）、什么时候结算、判据是什么，以及**它还没有进入校准，需要在 Web 上背书**。

## 边界

- **不要替用户编概率**。宁可未量化。
- **不要修改已冻结的判据或期限**——那需要走修订流程，且会留痕。
- 一条命令只做一件事；复杂决策拆成多条命题分别写入。
- 当事人说"稍后再说"时，不要纠缠：要么记成未量化命题，要么放弃，并说明你放弃了什么。
