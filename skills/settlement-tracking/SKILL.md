# 结算跟踪

捕获那半（`decision-capture`）把决策变成了可结算的预测；**这一半负责把它们结掉**。
两者合起来才是闭环——只有捕获没有跟踪，库里会积一堆永远不结算的题，而"永远不结算"
的样本不会报错，只是慢慢让所有读数失效。

## 为什么由拉取驱动

提醒的载体只有两个中性地方：**`AGENTS.md` 的一句约定**（会话开始时先拉一次）和
**本技能**（涉及复盘/到期时先拉）。刻意不做 pi 扩展、Claude hook、cron、守护进程
（ADR-0034 §二）：那些东西会把"这套流程能不能用"重新绑回某一个运行时或某一台常开
的机器上，而**失效时不会有任何报错**。

拉取式不是缺陷：它不依赖任何进程活着，没有推送凭据要管，也没有"提醒没到是因为服务
挂了"这一类故障。

## 回路

### 1. 拉队列

```bash
npm run --silent agent -- list-due
```

输出的**一个对象两栏**：

- `settleable`：到点了，而且有人能核实 ⇒ 这是**待办**。
- `dangling`：到点了，但**没人能核实**（只有他人的无来源确认，ADR-0031）⇒ 这不是待办，
  是"没法定论"。每项带一个 `reason`，成因只有一种：来源缺失。

**这两栏绝不能混。** 混在一起会让人把"没法定论"读成"我还没去结算"，于是他会去结算一条
本就不该由他定论的题——那正是 ADR-0031 要防的"替别人签字"。

### 2. 提醒有上限（ADR-0034 §四）

报**计数** + 最多 **3 条**最近的到期项，然后**停下**。不阻塞对话、不在每次回复里重复。
一条被忽略的提醒和不存在没有区别，而重复到被忽略只需要几次。

**另报一行未标领域计数**（ADR-0030 §八）：`untaggedDecisions > 0` 时说
“未标领域：N 条（补标：`list-untagged-decisions`）”。**没有到期项时也要报**——
那一行依附的是“你拉过一次队列”，不是“队列非空”；只在有到期项时顺带提，那句要求就落不了地。

**默认不主动结算**：结算是不可回退的（ADR-0020 的锁定单向性）。先说清楚要结算哪几条、
依据是什么，等用户点头。

### 3. 能核实的：带来源直接结算

```bash
npm run --silent agent -- settle \
  --question-id <id> --resolution YES \
  --source "https://data.example.org/cpi/2026-03" \
  --rationale "官网上月发布的 3 月 CPI 同比 2.4%，低于判据里的 2.5%"
```

- `--source` 是**给对方复核用的**，不是给你自己留的备注。没有它，这次结算只能约束你自己
  （ADR-0031）。
- `--resolution` 只能是 `YES` / `NO` / `AMBIGUOUS`。**判不出来就写 `AMBIGUOUS`**——
  它不产生任何分数，也不落库（ADR-0018）。编一个 `YES`/`NO` 会把噪音写进别人的校准。

`settle` 的返回值**三种模式**（授权矩阵见 ADR-0029）——**没有**单独的"提提案"命令：

| `mode`                  | 含义                                           | 接下来做什么                   |
| ----------------------- | ---------------------------------------------- | ------------------------------ |
| `settled`               | 真的结算了，来源已落库                         | 回报结果 + 依据                |
| `proposed`              | 降级成了提案（无来源，或该判据本就需他人确认） | 用 `list-proposals` 看等谁确认 |
| `requires-human-report` | 自我报告类，而且你不是当事人                   | **通知当事人**，不换身份重试   |

只有 `settled` 才算结算。看到 `proposed` 就当作"还在等确认"，**不要为了清空队列而凑一个
来源**——那会把"没人能核实"变成"看起来有人核实过"，比悬空更糟。

看等谁确认：

```bash
npm run --silent agent -- list-proposals
```

也**不要替别人确认**：只有"建题者或在该题上押过注的人"能确认，被拒时不要换身份重试。

```bash
npm run --silent agent -- decide-proposal --proposal-id <id> --accept
```

### 4. 回报结果

结算完成后，把**结果 + 依据**回报给用户（一句话），不要只报"已结算"。
用户需要知道的是"这条现在算 YES，依据是这个"，而不是你跑了几条命令。

## 悬空那一栏怎么办

`dangling` 里的题，用户是有出口的（ADR-0031 §五）：**补录可核查来源**。

```bash
npm run --silent agent -- record-resolution-source \
  --question-id <id> --source "https://…" --rationale "…"
```

补录后该题上**所有**预测计入，且**不会**回退任何锁定。但有一个前提：**来源必须是真的**。
你要做的是问用户"这条题现在有没有可查的来源？"，而不是自己编一个链接填空——那会把
"没人能核实"变成"看起来有人核实过"，比悬空更糟。

## 不做什么

- 不做 harness 专属物：没有扩展、hook、cron、守护进程（ADR-0034 §二）。
- 不为了"清空队列"把悬空项批量标成已结算或补一个假来源。
- 不在用户没确认前结算任何一条题。
