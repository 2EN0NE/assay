### Key Decisions

- Decision: 已结算预测不允许解绑，而不是"解绑时保留锁定判据"
- Rationale: 锁定的唯一判据是"该决策下是否有已结算预测"（事实驱动、不看 `rubricLockedAt`）。要在解绑后保住锁，就得引入第二个判据或让判据撒谎；少一条解绑路径比多一个可自证的锁便宜
- Decision: `AgentRecordPanel` 外层套无样式 div，而不是把它改成 forwardRef
- Rationale: 它没有 agent 痕迹时 `return null`，forwardRef 也拿不到 DOM 节点，v2 的 Transition 照样抛错
- Decision: 时序绕过（事后建决策再补清单）**未加判据**，只补了"挂上已结算预测即记锁定时点"
- Rationale: 决策当时没有已挂预测时，"这是不是事后补的"在数据上不可判定；硬加时点比较会误伤"把旧的已结算问题归到旧决策下"这类正当用法。要真正关闭需要产品决定，已写进代码注释与审查发现

### Lessons Learned

- **5 条 e2e 全红时，根因不是测试**：`Question.tsx` 的 `<Transition>` 被加了第二个子元素，HeadlessUI v2 因此抛错，`ErrorBoundary` 把每张卡片换成 "Something went wrong"。当时工作区里正在改断言（signIn exact、`getByText` exact），差点把应用崩溃当成测试问题收尾。教训与排查手法见 `knowledge/troubleshooting/headlessui-transition-v2-ref.md`
- 页面被 ErrorBoundary 盖住时，`error-context.md` 快照只有一句 "Something went wrong"；**组件栈在 `trace.zip` 的 `*-trace.trace` 里**，grep `transition.js` 一类的框架路径就能定位
- headlessui v2 的 `<Transition>` 两条硬约束：单子元素；子元素必须能把 ref 落到真实 DOM 节点（普通函数组件、`return null` 都不行）
- `invalidateQuestion` 只失效 `question.*` 查询，但 `AgentRecordPanel` 读的是 `agent.*`——新增读取方时容易漏掉失效，表现是"服务端写了、界面要刷新才看见"
- 本机 `npx playwright install chromium` 拉不到 CDN；用系统 Edge（`channel: "msedge"`）跑同一套用例是可行退路，已写进 README

- **`undefined !== null` 是真陷阱**：mock/fixture 缺字段时 `rubricLockedAt` 会变成 `undefined`，把"从未锁过"读成"锁过"（测试里当场踩到）。入口处 `?? null` 归一是值得的。
- **pi-lens 的 LSP 会缓存 `node_modules/.prisma/client`**：`prisma generate` 之后 LSP 仍按旧类型报错（连已删除的 `note` 列都还在），而 `tsc --noEmit --incremental false` 干净、磁盘上的客户端已是新类型。消除办法只有重启 LSP；本轮把 14 条按 false-positive 记下并留了证据。
- **e2e 的登录依赖 `AUTH_EMAIL_SERVER`**，而它此前既不在 `.env.example` 也不在 `e2e/README.md` 里——照文档做必然六个用例全红。已补进两处。
- **真正让那六个用例全红的是 `NEXTAUTH_URL` 的 scheme 与端口对不上**（已实测确认）：`.env` 里是 `https://localhost:3000/api/auth`，NextAuth 把它直接渲染进登录表单的 `action`，而 e2e 的 `webServer` 跑的是**明文 HTTP 的 3000** ⇒ 浏览器把 https 的 POST 打到只会 http 的端口 ⇒ `ERR_SSL_PROTOCOL_ERROR`，**请求根本没到服务器**（dev 日志里只有 `GET /api/auth/signin`，没有 POST）⇒ Mailpit 收不到信。修法：`dev:e2e` 把 `NEXTAUTH_URL`/`HOST_URL` 钉成 `http://localhost:3000`（`dotenv` 不覆盖已存在的环境变量，内联赋值有效）。
  - 教训：**“配置改对了却仍不生效”时，要去看请求到底有没有发出**（服务端日志的缺失比错误信息更有信息量：只有 GET 没有 POST，说明问题在浏览器侧，不在服务端）。
  - 我先前把它归因于“复用的 dev server 沿用了旧环境”，那是**错的**：与复用无关，是表单 action 指向了 https。已把 `e2e/README.md` 里的错误说明改成实测结论。

### Lessons Learned
- **`bash -n` 不是验证**：语法检查完全抓不到 `set -u` 下的运行时失败。`startup.sh` 里 `$skill_name（源在…` 紧跟**全角括号**，非 UTF-8 locale 下 bash 把那些字节算进变量名 ⇒ `unbound variable`，脚本当场死掉，而 `bash -n` 说“没问题”。**脚本类改动的验证必须是真跑一次**，并且 `$var` 后面跟非 ASCII 字符时一律写 `${var}`（审计脚本已留下，剩余地雷 0）。
- **移动文件要 grep 全部相对路径**：我只改了顶部两行 import，漏了文件深处的 `jest.mock("../lib/web/trpc", …)`，于是套件级失败（jest 报 “suite failed to run”，而用例计数看着还是“全过”）。**移动后必须 grep `"\.\./|"\./|require(`**。
- **验证要看套件数，不只看用例数**：失败的那次输出是 “1 failed, 28 suites / 348 passed”——用例数在涨、套件在挂，只看 “passed” 就会漏掉。
- 复查（code-review 技能，两轴并行子代理）确实抓到了我自己的测试与 tsc 都抓不到的东西：文档/ADR 与实现漂移、误触明文规则、以及那个脚本崩溃。**“测试全绿”不等于“规范全对”。**

### ② 悬空在复盘的可见性（业主裁定 A：在写入处挡住）

- **写入路径本来就是对的**：`scoreQuestion` 早在用 `meteredForecasts(settlementRecordOf(...))` 过滤，且有自证用例。真问题是**陈旧数据**（2 行改动前写入的 `QuestionScore`）+ **没有任何消费者渲染 §二/§三 的显示名**。
- 补做：重算受影响题（残留行 0）／`DANGLING_LABEL`、`CONFIRMED_BY_OTHER_LABEL`、`settlementLabelOf` 放进判据旁（一处措辞）／`decision.byId` 返回 `settlementScope` + `settlementLabel`／复盘页把"已揭晓没分数"拆成悬空与 ADR-0018 两个成因（纯函数 `unscoredCauses` + 单测）。

### Lessons Learned（本轮）
- **"数据脏"和"代码错"看起来一样，必须先分清**：我上一轮把 2 行陈旧数据讲成"计量泄漏"（持续违反），实际代码早就挡住了。判据差异：陈旧数据只影响已存在的行，代码错会持续生成新行——**去问"还能不能再造一行出来"，而不是只看现状**。
- **给页面写渲染测试前，先看它的 fixture 债**：这个复盘页要吃 15 个字段，页面级测试的成本远高于把逻辑提成纯函数。**逻辑提纯函数 + 页面只渲染**是更省的路。

### ③ 到期提醒里的未标领域计数（业主裁定 P1）

- 判据抽成 `untaggedDecisionWhere(userId)`（`domain_tags.ts`），列表与计数共用一处；`agent.listDue` 新增 `untaggedDecisions`。
- **P1 政策落地**：`>0` 就报，**与有没有到期项无关**（有单测钉住"两栏皆空时计数照样返回"）。技能、AGENTS.md、CLI 摘要三处文案同步。

### Lessons Learned（③）
- **锚点太通用 = 改到别处**：我给 `])` + `return {` 做替换，文件里有多处这样的块，于是我漏看的那一行（计数查询）根本没进去，`tsc` 立刻报"元组没有第 3 个元素"。**教训：锚点必须包含能把位置钉死的上下文**（`orderBy` 之类的邻居行），而**改完必须让编译器复核元组/签名**——这次是 `tsc` 接住的。
- **`jest.mock` 的工厂会静默吃掉新导出**：`jest.mock("./domain_tags", () => ({...}))` 让 `untaggedDecisionWhere` 变成 undefined。**给纯谓词用 `jest.requireActual` 取真实现**——mock 掉它等于把"两处共用同一判据"这件事测没了。

### ④ 两处重复（业主裁定 M1）

- **分桶：真的合并了。** 先证明两份实现逐条等价（10 等宽 / `>= 1` 钳位都有 / binCenter 同式 / 空桶同样 `binCenter` + `meanOutcome = NaN` / 输出四键一致），再提到 `lib/web/calibration_bins.ts` 的 `calibrationBinsOf`，`domain_stats` 与 `pages/api/calibration_graph.ts` 共用。**行为等价有证据**：两个消费者的既有测试（含 fixture 的 0.64/−0.64/恰好 0）全绿。另加 `calibration_bins.test.ts` 直接钉住钳位、边界、空桶 NaN。
- **投影：查清后没有可合并的重复。** `toPredictionView`（队列：resolveBy/oracleKind/quantified/latestForecast）与复盘视图（resolution/score）**字段集合本就不同**；真正必须一致的部分（§二/§三 的判定与措辞）已经在 `settlement_scope.ts` 里只有一份。硬合并会造出一个两个面都用不全的联合类型——那是重新引入复杂度，不是消重。**记录该结论，不再动它。**

### Lessons Learned（④）
- 复查给的"重复"要**先证明等价再合并**：这次两边连钳位都恰好一样，合并才敢做；如果当时只有一边带钳位，合并就会把一个**越界 bug** 悄悄修掉或悄悄引入。
- **"看起来重复" ≠ "可合并"**：两个投影字段不同、共享的只有 3 个字段，"合并"只会产出一个谁都用不全的类型。判断标准是**"是否存在一个必须一致的量"**——分桶有（同一个人在两处必须看到同一个形状），投影没有。

### ⑤ danglingReason 的"空串契约"（业主裁定 N1）

- 参数收窄为 `SettlementRecord & { resolutionSource: null }`，新增类型守卫 `isDangling`（§六 判据的直接推论）；空串分支消失，调用点（队列）改用守卫收窄类型。
- 仓库 eslint 的 `no-unused-vars` **不认 `_` 前缀** ⇒ 与其改 lint 配置，不如让参数真的被用到：边界上断言"来源必为 null"，越界（有人 `as` 绕过）就**抛**，而不是静默返回空话。并为这个守卫补了用例。
- 那条"固定怪契约"的断言（有来源时返回 `""`）随之删掉。

### ⑥ pi-lens 相关物（业主裁定 H3）

- 删掉 `import_router.ts` 里那两处 `pi-lens-ignore: typescript:2322`（连同解释性注释）——它们是**工具 bug 的补丁**（会话内语言服务器持有陈旧 Prisma 快照），与仓库原有的 3 处（抑制 `no-eval` / `no-open-redirect` / `unchecked-throwing-call` 这类**真实安全规则**）性质不同。混在一起会让"忽略标记"这个信号贬值。
- `.pi-lens.json` 加进 `.gitignore`（它关的是**本机**被误选的 deno 服务器——机器级配置，不属于仓库）。

### 关于 pi-lens 的标准与工程标准是否一致（业主问）
- **格式化：一致。** 它重排过的文件经仓库口径（Prettier `--check`）全部通过 ⇒ 输出与 Prettier 兼容。
- **规则集合：不一致。** 它额外跑仓库门禁不管的规则（Markdown MD060、对 `scripts/` 也报 `no-console`），且其 TypeScript 诊断来自**可能持有陈旧快照**的语言服务器（本会话那批 2322 误报即由此而来）。
- **结论（写入 AGENTS.md）**：本仓库的判定标准是 `tsc` + `next lint` + `jest`；pi-lens 的额外规则是参考，不是门禁。

### ⑦ 迁移升级验证脚本的去留（业主裁定 V1）

- 先澄清事实：它**不是上游/fork 遗产**，也不是本轮临时造的——整个 `scripts/` 未跟踪，文件创建于今天，出自 `.pi/todos/c5b45af1.md`（测试审计，P1 项），且**已在 CI 里跑**（`test.yml:81`）。
- 它解决的是空库 CI 抓不到的事：**已经装着数据的库**升级后对不对（两条回填的口径 + 大小写冲突必须大声失败）。
- **V1 落地**：AGENTS.md 的「验证规范」新增一节**白话版**（讲清"回填"是什么、为什么空库 CI 会骗人、什么时候不用管、什么时候必须补检查），脚本头部加指针（把迁移加进 `UPGRADE_MIGRATIONS` + 补断言）。
- 关键理由（也写进了 AGENTS.md）：脚本只认识写死的那几条，**新迁移不会自动跟随** ⇒ 不立规矩的话，CI 的绿灯与本次改动无关，**比没有门禁更糟**。

### 本轮七项裁决的共同教训
- **先核事实再下结论**：七项里有 **3 项**（①④⑤→ 其中 ① 是"我读错 ADR"、④ 是"投影没有真重复"、⑦ 是"并非无票据"）在我查证后**改变了原来的判断**。复查报告与我的复述都可能不全对——**每条都要回到代码/数据/CI 去核**。
- 查证手段很有用：**真库 SQL**（悬空却带分数的行数）、**git 身份**（未跟踪 vs 已提交，判断"这是谁的产物"）、**CI 配置**（判断"这道门禁到底守没守"）。
