## Problem Statement

系统现在能记下"我认为 X 有 70% 概率"，但**记不下"我当时为什么这么判断"**。后果有三：

1. **复盘时只有结果侧。** 打开一条已结算的 Question，能看到 YES/NO、Brier、相对分，却看不到当初的推理。于是无法把 Decision Quality 与 Outcome Quality 分开看——只能靠记忆，而记忆在结果已知后必然被污染（Resulting）。
2. **决策过程没有被要求走完。** 备选方案、事前剖析、参考基准率、"我可能错在哪"，这些是 Decision Quality 里**可查证**的部分，但当前没有任何机制要求在决策时点做一遍，复盘时也就无从诊断"漏了哪一步"。
3. **Predictions 是孤儿。** 一个决策常拆出多个 Prediction，现在它们只是一堆互不相干的 Question；"这几个是一起为同一个决策下注的"这一事实没有落点。

## Solution

把 **Decision 升为一等实体**。一次决策由三部分组成：

1. **推理过程（叙事）** —— 决策陈述、理由、预期后果、当时已知信息、当时未知信息。在决策时点写下，之后不可静默改写：**改写已填写的内容必须带理由并留痕**（[ADR-0012](../../adr/0012-revisions-must-leave-a-trace.md)），CLI 的 `update-narrative` 是唯一入口。
2. **过程清单（Decision Rubric）** —— 一张条目化的检查清单，每条只记**可查证的事实**（做到 / 没做到），在**决策当时**填写。不给当事人自评分，分值由清单完成度**推导**（分母取该决策所属**决策版本**的条目集合）。它的价值在诊断力：清单告诉你**漏了哪一步**，一个分值什么也不说。
3. **0..n 个 Prediction** —— 复用现有 `Question` + `Forecast`，因此自动继承结算、校准、判据类型、录入来源、背书、修订留痕等全部既有能力。

再加一个**复盘视图**：把"决策时记录"（推理 + 清单）与"最终结果"（各 Prediction 的结算与分数）并排呈现，两者在界面上不混淆、在存储上更不互相污染——结果揭晓后清单**不可再改**，因为那时已没有不事后美化的理由。

## User Stories

1. 作为一个决策者，我想在决策当时把决策陈述、理由、预期后果写下来，以便结果揭晓后能回看"我当时怎么想的"，而不是靠被结果污染的记忆。
2. 作为一个决策者，我想分别记录**当时已知的信息**与**当时未知的信息**，以便复盘时判断"这算想不到还是本该想到"。
3. 作为一个决策者，我想把一个决策拆成 0..n 个可结算的 Prediction，以便一部分信念能被校准，另一部分（比如"这决定会让我更满足"）也能被记着。
4. 作为一个决策者，我想让"这几条 Prediction 是同一个决策下注的"成为结构化事实，而不是靠标题里的措辞或 tag 猜。
5. 作为一个决策者，我想在决策当时逐条回答过程清单，以便 Decision Quality 有可查证的记录，而不是一个自评分。
6. 作为一个决策者，我想清单每条只回答"做到 / 没做到"，以便它可被他人复核——3 分与 4 分的区别无人能核，而"有没有写下备选方案"能。
7. 作为一个决策者，我想看到"5 项做到 3 项"这样的完成度，以便知道这次决策漏了哪一步，而不是只知道它"大概还行"。
8. 作为一个决策者，我不希望决策质量分被卷进排行榜或相对分，以便它不会变成新的"敷衍数字"（Compliance Number）。
9. 作为一个决策者，我想在一个页面上同时看到"决策时的记录"与"最终结果"，以便一眼分辨我这次是"决策好"还是"运气好"。
10. 作为一个决策者，我想让清单一经填写便在结果揭晓后锁定，以便复盘材料不能被事后美化。
11. 作为一个决策者，我想让清单条目集合本身可以演进（增删条目），以便它随我实践的增长而调整。
12. 作为一个决策者，我想让**已有决策的历史解释不因清单演进被改写**，以便"第 5 条当时没做"不会因为第 5 条被删掉而变成"当时全做了"。
13. 作为一个 Agent，我想用一条命令创建一个 Decision 并声明它的叙事字段，以便在对话中捕获决策后立刻落库。
14. 作为一个 Agent，我想用一条命令把一条 Prediction 挂到一个 Decision 上（或创建时一并挂上），以便拆解结果能结构化保存。
15. 作为一个 Agent，我想用一条命令写入清单各条的完成情况，以便清单在决策当时被记录，而不是只被问过。
16. 作为一个 Agent，我想用一条命令读回某个 Decision 的完整复盘材料（叙事 + 清单 + 各 Prediction 的状态与分数），以便在一次独立上下文的跟踪调用里做复盘。
17. 作为一个 Agent，我想让所有决策相关命令的 stdout 只有确定性 JSON、日志一律走 stderr，以便我在独立上下文里可靠解析（沿用 ADR-0015 的契约）。
18. 作为一个人，我想在 Web 上看到决策详情页（推理 + 清单 + 挂着的 Predictions），以便不做 CLI 也能复盘。
19. 作为一个人，我想在决策列表上同时看到"质量分"与"结果分"，以便区分这两件事。
20. 作为一个人，我想能在 Web 上直接创建/编辑决策的叙事与清单，以便人是最可信的兜底输入源（ADR-0007）。
21. 作为一个决策者，我想让"没有拆出任何可验证命题"的决策也是合法状态，以便"我还没想清楚要验证什么"不会挡住记录。
22. 作为一个决策者，我想让一条 Prediction 至多归属一个 Decision，以便复盘视图不会重复计算同一条预测。
23. 作为一个决策者，我想让不挂 Decision 的普通 Question 继续正常工作，以便现有功能零回归。
24. 作为一个决策者，我想在复盘时看到"当时写下的备选方案"（在叙事里）与"最终选了什么、结果如何"，以便直接对照。
25. 作为一个 Agent，我想让决策质量层的清单问答与预测捕获层的问答（概率 / 期限 / 判据）是**两层独立脚本**，以便不把两套问法混成一堆审讯（ADR-0016 的分层）。

## Implementation Decisions

### 模块与schema

- **新增 `Decision` 模型**：叙事字段 + 归属用户 + 时间戳。
  - `statement`（决策陈述，必填）、`reasoning`（理由）、`expectedOutcome`（预期后果）、`knownInfo`（当时已知）、`unknownInfo`（当时未知）。
  - `userId`（决策者）、`createdAt`、以及**清单锁定时间** `rubricLockedAt`（见下）。
  - `rubricVersion`（**决策版本**，见下）：该决策计分时适用的条目集合版本。
  - `rubricRecordedAfterOutcomeAt`：清单写在**结果揭晓之后**的时点标记（ADR-0020 第六点）。
- **新增清单完成情况记录表**（每条一行，而非只存一个总分）：
  - `decisionId`、`itemKey`、`status`（做到 / 没做到）、`recordedAt`。
  - `itemKey` 存**稳定标识**而不是文案，历史语义因此不随文案或条目集合演进被改写（对应 User Story 12）。
  - **不带 per-item 自由文本**：条目的证据与细节落在叙事字段与各 Prediction 的判据上，对应关系见 ADR-0016。
- **清单条目集合是代码常量**：`itemKey` + 展示文案 + 顺序。初始五条来自 ADR-0016：备选方案 ≥ 2 / 事前剖析 / 参考基准率 / 写下"我可能错在哪" / 判据可证伪且已冻结。
  - 理由：条目集合是**产品语义**，不是用户数据；放代码里可随**代码版本**演进、可被测试覆盖，且不需要 "清单定义表" 这层间接。
  - **条目增删必须新建一个决策版本，既有版本的条目列表不得改写**（ADR-0020 第四点）：历史决策按自己的版本解释，因此"后来删掉一条"不会让历史分变好看，"后来新增一条"也不会让它掉下来。`Decision.rubricVersion` 记录所属版本。
- **`Question` 增加可空外键 `decisionId`**（`onDelete: SetNull`）：Prediction 复用现有实体，关联是**加成**而非改建。
  - `SetNull` 的理由：删掉一个决策的容器，不该连带删除已冻结的、可能已结算并计入校准的 Prediction——那是数据丢失。
- **决策质量分不落库**：由清单完成情况**推导**（该决策版本内的 `completed / total`）。落库的分值必然过期（清单条目会演进），而推导值永远与事实一致。

### 接口

- **纯领域模块**（新增，最大的一块）：清单条目定义、完成情况的校验与规范化、质量分推导、以及"结果揭晓后不可改清单"的判定。它是唯一需要被广泛测试的模块。
- **tRPC router**（新增 `decision_router`）：创建 / 读写叙事 / 写清单 / 查询详情与列表。沿用现有 router 的鉴权与 Zod 校验惯例。
  - 详情查询（`byId` / `show-decision`）回**逐条** Prediction 的状态与分数（User Story 16）：分数**直接取 `QuestionScore` 已存的值**，不新增计分口径——`absoluteScore` 恒有，`relativeScore` 只在 `isRelativeScored`（公共事实类）下有值、否则为 `NULL`（ADR-0002 的落地面，见 AGENTS.md「可观测性契约」），未结算则没有分数行。
  - **不做决策级聚合分**：把多条 Prediction 的分数揉成一个"决策结果分"是一个新指标，归 ADR-0002 管辖。列表页因此只给事实（清单 done/total、已揭晓 N/共 M）。
- **CLI 子命令**（沿用 ADR-0015 的命令形态与 stdout 契约）：创建决策、挂 Prediction、写清单、读回复盘材料。
- **Web**：新增决策列表页与详情页（详情页承担复盘视图的"并排"职责）。
  - **交付现状（如实说明）**：本次交付里 Web 是**只读**的（`pages/decisions/*` 仅 `useQuery`），
    决策与清单的**写入入口只有 CLI / skill**。因此 ADR-0020 的"结算后只读"在界面上不可验证，
    真正的拒绝在服务端（`decision.setRubric` → `CONFLICT`），并由 e2e 断言。
    叙事另有 `update-narrative`（补写空字段自由；改写已填写内容须带理由并留痕，见 ADR-0012）——
    即“读**写**叙事”这条由 CLI 兼现，Web 侧仍只读。
    User Story 20 的"人在 Web 上直接创建 / 编辑"**推迟**到需要时再做：它的阻塞理由（"先补齐写入入口"）
    对叙事已解除、对清单仍未——清单的写入入口只有 CLI。

### 数据流与不变量

- 决策叙事与清单可在**决策当时及之后**修改，直到该决策下**任一 Prediction 被结算**——此后清单锁定。这是"清单在决策当时填写"的可执行化，也是 Resulting 的结构性防线。
- **锁单向、不可回退**：判据 = "该决策下有已结算的 Prediction"（事实）**或** 已记录的 `rubricLockedAt`。撤销结算会打印出 `resolved = false`，这时只看事实就会重新开门（`undoQuestionResolution` 正是这条路径）；已结算的 Prediction 也不允许解绑。
- 锁定时点在两处写入：**结算路径**（该 Question 已属某 Decision 时）与**挂载一条已结算的 Prediction** 时。
- **清单写在结果揭晓之后的会被标记**（`rubricRecordedAfterOutcomeAt`）："先建决策 → 补满清单 → 再挂一条已结算的 Prediction"是唯一剩下的绕过路径（写清单时该决策名下没有任何预测），标记让它在复盘时不再与"当初填的"同形。
- 质量分**只**依赖清单完成情况，不读任何结算结果，因此与结果分天然脱钩。
- 一个 `Decision` 的 `Predictions` 数量可以是 0（对应 User Story 21）。
- 无法被外部事实判定真伪的预估（如"这决定会让我更满足"）：**不另开通道**，落为 `oracleKind = SELF_REPORT` 的普通 Question（ADR-0002 已把它定为一等判据类型，ADR-0011 已允许它带 0 个 Forecast），因此它同样通过 `decisionId` 归属到 Decision。这是对 ADR-0001 遗留未决项的落地。

### 文档一致性（本 phase 附带修正）

- `CONTEXT.md` 的 `Decision Rubric / 决策量表` 词条：**标题**仍写着"量表"（与 ADR-0016 的最终决定"由清单条目构成、不自评"矛盾），**正文已经是对的**。本次把它改为 `Decision Rubric / 决策清单`，并补两句（分母取**决策版本**、结算后只读），另新增 `Decision Version / 决策版本` 词条。

## Testing Decisions

- **测什么**：只测**外部可观察的行为**，不测实现细节。好的测试形如：
  - "清单 5 项做到 3 项 ⇒ 完成度 3/5"（而不是"内部计数器被调用了三次"）
  - "决策下任一 Prediction 已结算后，写清单被拒绝"（而不是"某标志位为 true"）
  - "清单条目集合删掉一条后，历史决策的记录仍显示当初那 5 条"（语义稳定性）
- **测试 seams（须与作者确认）**：全部**复用既有 seam，不新开**。

  | #   | seam                                                      | 覆盖                                 | 既有先例                                                                |
  | --- | --------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------- |
  | S1  | 纯领域模块（清单定义 / 完成度推导 / 锁定判定 / 输入校验） | 绝大部分逻辑                         | `lib/web/revisions.test.ts`（`planRevisions`、`missingRevisionReason`） |
  | S2  | tRPC router，经 `createCaller` 直调                       | 鉴权、校验、落库副作用、跨实体不变量 | `lib/web/agent_router.test.ts`、`lib/web/resolution.test.ts`            |
  | S3  | CLI 命令                                                  | 参数解析与 stdout JSON 形状          | `cli/commands.test.ts`、`cli/args.test.ts`                              |
  | S4  | 复盘视图                                                  | 并排呈现与锁定后的只读表现           | `e2e/agent-cli.spec.ts`（Playwright）                                   |

- **不新增 seam**：S1 是唯一的新模块，但它落在既有的"纯领域模块 + 共置单测"惯例上（`revisions.ts` / `calibration.ts` 同形）。
  - 跨模块的**架构不变量**（"决策质量分不得读取结算结果"）不用测试表达，改用 **ESLint 的 `no-restricted-imports`**：断言源码文本的测试会命中注释（误报）、又会漏掉经 barrel 的 re-export，且它本身就是 S1–S4 之外的新 seam。lint 是 AST 语义的，并且已被既有门禁覆盖；已知盲区是 barrel 路径（将来若要图级强制，应换依赖图工具，而不是再写一个自研文本断言）。
- **e2e 的已知限制**：本机 Playwright 自带 chromium 下载不下来（`cdn.playwright.dev` 不可达）；
  已改用系统 Edge（同为 Chromium 内核）跑通全部用例，CI 仍用 chromium。
  首次跑通时发现的三条非测试问题见 [ticket 06](./06-review-view-side-by-side.md)。

## Out of Scope

- **Phase 3 的决策卫生工具**：`Pre-mortem` / `Kill Criteria` / `Ulysses Contract`。清单里的"事前剖析"一项只记录**有没有做**，**不提供**引导流程、不设定时提醒。这是 ADR-0016 的清单与 Phase 3 工具的分界。
- **Phase 4 多人决策**（名义群体法 / 寻真小组 / 盲测咨询 / DRI）。
- **Phase 5 主动偏差诊断**。
- **决策质量的排行榜或相对分**：ADR-0002 的相对分只给公共事实类的 Forecast；质量分不进任何排行榜（User Story 8）。
- **决策列表/详情的数据可视化**（图表、趋势），先做并排文本与表格。
- **app 内 LLM 入口**：ADR 已定不接线，本 phase 不动。
- **对既有 Question / 结算 / 计分行为的任何改变**：本 phase 纯加成，现有功能零回归。

| 6   | 复盘视图的落点                                | **新增决策详情页**（列表页 + 详情页），不动现有 `/q/[id]`             | 决策是独立实体；"并排"是两个视角的并列，塞进预测页会让两种视角互相污染         |
| 7   | 清单锁定时点                                  | 该决策下**任一 Prediction 已结算**即锁定                              | 把"决策当时填写"变成可执行约束；结算前仍可改（含补记），结算后不可             |
| 8   | 是否本 phase 就引入"决策质量清单问答"进 skill | **是**，但作为**独立于预测捕获层的第二段脚本**                        | ADR-0016 明确要求分层交付、不与概率/期限/判据的问法混成一套                    |

## Further Notes

- **为什么这一 phase 值得先做**：`Decision Quality` 与 `Outcome Quality` 的分离是整个系统的核心原则 1，而它此前只落在文档里；`Decision` 实体是其余所有 phase（3 的卫生工具、4 的多人、5 的偏差诊断）的挂载点。
- **为什么不能用自评量表**：本系统刚为防 `Compliance Number` 给追问设了显式出口（ADR-0010 / ADR-0011）。一个 1–5 分的自评**就是一个新的敷衍数字**，且不可查证。清单的每一条都是可查证的事实。
- **与 Phase 1 的关系**：Phase 1（MVP，已实现）只兑现 ADR-0001 的另一半——Prediction 复用 `Question`/`Forecast` 并挂上判据类型 / 录入来源 / 背书三个语义字段。本 phase 不重做那部分。
- **验收（沿用 roadmap Phase 2）**：任一决策可回看"当时的理由"，并能给出与结果脱钩的决策质量评估。可验证化为：创建带清单的决策 → 挂上并结算一条 Prediction → 在复盘视图看到"清单完成度"与"结算结果"并排，且清单此时已不可改。
