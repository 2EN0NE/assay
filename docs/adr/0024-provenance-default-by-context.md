# 记录来源的默认方向按调用上下文分叉

现状是 fail-open：`create-prediction` **不给** `--agent-collected` 就等于「数字由当事人给出」、天然已背书。但 [ADR-0008](./0008-endorsement-required-for-agent-collected.md) 的理由恰恰是"未经当事人背书的 Agent 搜集记录不得进入校准"——而这个默认值把漏标的后果放在了危险的一侧：**代理编出来的数字会被当成人的判断**，并且这类记录"通过了背书的形式要件"，事后最难识别（见 CONTEXT.md 的 Compliance Number）。

改为按**调用上下文**决定默认方向：

| 调用上下文                                              | 默认来源                 | 谁能推翻              |
| ------------------------------------------------------- | ------------------------ | --------------------- |
| 有 `AI_AGENT=pi` / `PI_CODING_AGENT=true`（Agent 代行） | **未背书，待当事人确认** | 只有当事人的显式声明  |
| 无上述标记（人自己在终端里敲）                          | 已背书（`HUMAN`）        | 显式声明为 Agent 搜集 |
| HTTP 面带 apiKey（`/api/v0/*`）                         | 同「Agent 代行」一档     | 显式声明              |

**标记只决定默认方向，并作为审计线索；权威仍是显式声明加背书。** pi 的文档写明这两个标记的用途就是"让子进程识别 Pi 是拉起它的 agent"，且子进程会继承它们——所以 CLI **能**分辨"这条命令是不是从 pi 会话里发出的"，但**分辨不出"这个数字是谁给的"**：同一条 `create-prediction --probability 0.7`，由当事人说出的与由代理编造的，在传输层完全一样。标记不能替代声明，只能让默认方向少犯一类错。

## Considered Options

- **① 保持现状（默认已背书）**：漏标即冒充人的判断，且留下的记录形式完备、事后无从分辨。
- **② 一律从紧（所有调用都默认未背书）**：安全，但把人自己在终端里敲的那条路也一起收紧，徒增摩擦——而这恰恰是最不需要收紧的一条。
- **③ 来源必填、无默认**：同上，且让最常见的那条命令变得难用。

## Consequences

- `create-prediction` 的默认极性要倒过来：`--agent-collected` 从"特例标记"变成"默认那一档"。
- **无标记不等于"人打的"**：Pi 经 SDK 嵌入时不设标记，脚本与 cron 也不设。这条分支仍按 `HUMAN` 落库，但调用上下文必须可审计，否则误分类无法复查（审计元数据是否落库、落在哪，另议）。
- skill 需要同步：它现在依赖"默认即当事人给的"来少写一个 flag；极性倒过来之后，代理代当事人记录时要么显式声明来源，要么让当事人事后背书。
- 与 [ADR-0008](./0008-endorsement-required-for-agent-collected.md) 的分工不变：本 ADR 只决定"未声明时默认落在哪一侧"，背书仍是把某个数字认定为当事人信念的唯一动作。
