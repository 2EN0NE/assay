# 站内是唯一内置触达通道；外部触达经 pi 插件，本工程只预留接口

提醒与结算提案的**内置触达通道只有站内**（`Notification`）。外部通道（Telegram、微信及未来新增者）**不由本工程发送**，而是由 **pi 侧的消息插件**承担：本工程只负责把"待触达"的东西暴露出来，预留一个可被插件消费的接口（`S` = ②）。

这一刀比"站内 + 邮件"切得更彻底：**项目里已有的 Postmark 通知通道（`lib/web/notifications.tsx`）不进 MVP**，也不补 SMTP 替身。理由是触达本质上属于**当事人的个人基础设施**，不是这个产品的职责——当事人已经在 pi 里配置自己的消息插件，产品再自带一套邮件发送，等于制造第二个配置面、第二条会腐烂的凭据链（`POSTMARK_API_TOKEN` 至今连 `.env.example` 都没有），而且它**在本地不可验证**（Mailpit 只接 SMTP，接不到 Postmark 的 HTTP）。

这与 ADR-0005 是同一条线：跟踪本身已经是一次普通 pi 调用，那么"跑完跟踪、要提醒当事人"交给同一个 pi 上下文顺带完成即可，产品不需要再建一条投递管道。

## Considered Options

- **① 站内 + 邮件（统一走 SMTP）**：本地可验证，但把邮件的配置与凭据责任放进产品，与"触达属于个人基础设施"的判断相悖。
- **③ 仅邮件**：把最不可验证的一条通道当作唯一通道。

## Consequences

- 需要一个**待触达的对外接口**（delivery interface）：pi 插件按它拉取待发送内容，并回报发送结果。
- 内置只渲染站内通知；`/notifications` 是**兜底页面**——任何外部通道失效时，站内始终可见。
- Postmark 相关代码与 `POSTMARK_API_TOKEN` 在 MVP 中不使用；是否删除留待后续。
- 具体插件清单与接口契约待当事人提供后补记（已知：当前全局扩展与 npm 记录中**未安装**任何 telegram / 微信插件）。
