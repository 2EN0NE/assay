# 决策清单：条目是代码常量，取值只有二值，分值按决策版本推导，结算即锁定

[ADR-0016](./0016-decision-quality-as-checklist.md) 定了"决策质量记成可查证的过程清单、不自评"。实现它需要补六个此前未定的点：

**一、清单条目集合是代码常量，不是数据表。** 条目（`itemKey` + 展示文案 + 顺序）**随代码版本演进**，被测试覆盖。完成情况里存**稳定标识**而非文案，因此文案改写不会改写历史语义。不引入"清单定义表"：条目是产品语义，不是用户数据，多一层间接只会换来无人使用的"可配置性"。

**二、每条只有"做到 / 没做到"，没有"不适用"。** 引入 N/A 会立刻产生一个自我开脱的口子，而这正是 ADR-0016 拒绝自评量表的同一条理由——它不可查证。"这段决策确实不需要事前剖析"这种判断，恰恰是最需要被外部复核的那一类。

**三、完成度是推导值，不落库。** 分值 = 做到项数 / **该决策所属决策版本所含的条目数**（见四）。落库的分值必然过期（条目集合会演进），推导值则永远与事实一致，且结构上**不可能**读取任何结算结果——这是 Decision Quality 与 Outcome Quality 脱钩在实现层的保证，不靠约定。

**四、条目集合按"决策版本"演进，历史决策按自己的版本解释。** ADR-0016 已定条目可增删，因此必须有一个东西固定"当年用的是哪一套"：**任何增删都新建一个决策版本，既有版本的条目列表不得被改写**；`Decision.rubricVersion` 记录该决策计分时适用的版本。这是"历史语义不随演进被改写"的落地方式——若允许改写既有版本的条目列表，一次"顺手调整顺序或文案"就会改掉所有历史决策的分母，而**不会有任何用例失败**。

- 与"并集"口径（当前集合 ∪ 记录里出现过的条目）的差别落在**新增**那一侧：并集会给历史决策扣上一个当时并不存在的义务，于是清单一成熟，整段历史逐年下沉，制造出"决策质量在下降"的假象。按版本解释时，新条目只对新建的决策适用。
- 代价是一张版本表（代码常量 + `Decision` 上一个整数）。**那张表只有在条目第一次增删时才需要多一行**；在那之前它只有一行。

**五、锁定单向、不可回退。** 该 Decision 下任一 Prediction 已结算，清单即锁定。判据 = **事实 ∨ 已记录的锁定时点**：

- 事实：该决策下存在已结算的 Prediction（`findLockingPrediction`）。
- 时点：`Decision.rubricLockedAt`，在任何"把 Prediction 变成已结算"的路径上写入——结算时该 Question 已属某 Decision，或挂载一条**已结算**的 Prediction 时。
- 只看事实会漏掉一条**已经存在**的路径：`undoQuestionResolution` 把 `resolved` 置回 `false`，于是"该决策下有已结算的 Prediction"不再成立，门重新打开。锁单向是本 ADR 的主张，所以判据取"∨"：一旦锁过，就永远锁着。
- 清单锁定后**只读**（服务端拒绝，`CONFLICT`），叙事字段仍可补充——叙事不被评分，事后补充它不产生激励扭曲。但**改写已填写的叙事须带理由并留痕**（[ADR-0012](./0012-revisions-must-leave-a-trace.md)）：叙事漂移与判据漂移一样，危险来自"无声"。

**六、清单写在结果揭晓之后的，单独记下来。** 挂载一条**已结算**的 Prediction 时，若该决策清单的写入时点（各条 `recordedAt` 的最大值）晚于该 Prediction 的 `resolvedAt`，落库标记（`rubricRecordedAfterOutcomeAt`）。

- 它堵住的是唯一剩下的绕过路径：**先建决策、补满清单、再把一条已结算的 Prediction 挂上来**——写清单时该决策名下没有任何预测，锁无从察觉。
- **为什么落库而不是推导**：单向性要的是"事件"，而推导只能描述"现在"。这件事的输入会变（撤销结算会把 `resolvedAt` 清空），推导出来的标记会随之消失，而它**已经发生过**。
- 呈现为"清单为结果揭晓后记录"。它不改变分值算法，只让"当初填的"与"事后补的"在复盘时不再同形。

## Considered Options

- **清单定义表（可配置条目）**：条目变成用户数据 → 需要迁移/版本/兼容，且没人会配；语义稳定性还得另想办法。
- **允许 N/A**：见上，自我开脱入口。
- **落库分值**：方便排序 → 但排序本身是我们要避免的（见 ADR-0002：相对分只给公共事实类的 Forecast；质量分不进任何排行榜），而落库的分值在条目演进后会说谎。
- **按"当前条目集合"计分**（不分版本）：实现最简 → 但删掉一条会让历史完成度**升高**（分母变小、分子不变），是**自利方向**的篡改：删清单一栏就能让历史分变好看。
- **并集口径**（当前集合 ∪ 记录中出现过的条目）：它在"新增条目"这一侧会逐年制造假性质量下滑（见四）。
- **以"事实"为唯一锁定判据**：更"纯" → 但撤销结算即可开门（见五）。
- **以时点为唯一锁定判据**（"锁 = `rubricLockedAt !== null`"）：会漏掉"事实已成立、时点尚未写入"的窗口（结算路径与写入之间崩溃）→ 故取"∨"，两种判据各补对方的洞。
- **结算后仍可改清单**：给"补记"留空间 → 但无法区分补记与美化，等于把防线交给自觉。
- **按时间锁定（如决策后 N 天）**：与"决策当时"无关，且会误伤真的还没结算的决策。

## Consequences

- 清单的读写是一条纯函数式的领域逻辑（条目定义、完成情况校验与规范化、完成度推导、锁定判定），可在不碰数据库的前提下被充分测试。
- 历史决策的清单解释**不随条目集合演进被改写**：它按自己的决策版本解释，因此某条目后来被删掉或新增，都不会改变当初那一次的解释与分值。
- 锁定不改变叙事字段的可写性，因此复盘时补充"现在回看，我当时低估了什么"仍然可行——写入入口是 CLI 的 `update-narrative`；改写已填写的内容须带理由并留痕（ADR-0012）。
- **锁单向**：结算后来被撤销，或 Prediction 被解绑（已结算的**不允许**解绑），都不会让清单重新可写。
- **没有解锁入口。** 确实写错了只能在数据库里手工改（同时清 `rubricLockedAt` 与 `rubricRecordedAfterOutcomeAt`），这条路径**不留痕**——因此它只适用于纠错。若人工修复变得频繁，应当改用 ADR-0012 的正式路径（带理由 + 留痕），而不是继续改库。
- 清单不记录 per-item 自由文本：条目的证据与细节落在叙事字段与各 Prediction 的判据上，对应关系见 ADR-0016。
