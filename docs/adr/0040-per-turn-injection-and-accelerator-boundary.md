# 每轮注入与加速器边界：pi 扩展只负责「到达」，删掉它回路仍完整

[ADR-0034](./0034-tracking-is-pull-based.md) 第二点写死了一件事：**不提供 pi 扩展**。理由不是洁癖，而是**失败可见性**——「任何只在一个运行时里能用的东西，都会把"这套东西能不能用"重新绑回那个运行时」，而绑定失效时**不会报错**。

那条禁令成立的前提是：提醒的载体可以完全中立（`AGENTS.md` 一句 + skill 的触发条件）。实际使用暴露了它的剩余漏洞：**"谁去拉"仍然是模型**。模型弱一点、上下文脏一点、任务紧一点，那一句就不执行——而它不执行时，会话里没有任何痕迹说明"提醒本该出现"。这与 [ADR-0038](./0038-unrecorded-is-not-not-done.md) 处理的是同一个病：**"机制没工作"与"本来没事"同形**。

于是需要一个真正能"替模型执行"的东西。它在 pi 里存在（`session_start` / `before_agent_start` 事件，已核 `docs/extensions.md`），所以本 ADR 要做的不是否认它有用，而是**给它划一条不破坏 ADR-0034 理由的边界**。

**一、基线与加速器，判据是"删掉它还完整吗"。**

|                           | 定义                                              | 内容                                                      |
| ------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| **基线（Baseline）**      | 不依赖任何 harness 也能走完回路的最小载体集合     | `agent.brief` 等下钻命令 + **自足的 `AGENTS.md`** + skill |
| **加速器（Accelerator）** | 只在某个 harness 内存在，**只负责"到达"**的附加物 | pi 扩展：把 `brief` 的输出按 turn 注入                    |

**验收判据只有一条**：删掉加速器，回路仍然完整——`docs/uat-pi-agent.md` 的基线路径必须在不装扩展时全绿。没有这条，加速器会在一周内变成主通道（这正是 ADR-0034 Considered Options 里那句"体验最好 → 但它把可用性绑回 pi"所指的滑坡）。

**二、抓手上限：它可以增加"到达率"，不可能增加"执行率"。**
扩展注入的是文字。模型仍然可以不据此行动。真正压住"知道但没做"的是另外两层：**结构层**（必填项、冻结后拒绝写入）与**返回值层**（`create-decision` 的返回里就带"清单未记录"）。本 ADR 不把"模型不遗漏"押在扩展上——那会重犯 ADR-0034 的错误，只是换了个位置：从"押在模型守约"变成"押在某个插件作者守约"。

**三、注入位置：`before_agent_start` 的 guideline 段，绝不并入用户消息正文。**
状态块作为 turn-local 的 guideline 注入，带显式标签：

```
<fatebook-status generated-at="…" state="live">
未结算 38：逾期 0 / 一周内 8 / 一月内 10 / 一月以上 20
…
</fatebook-status>
```

**为什么不能拼进用户消息**（虽然那样最省事）：

- **归属会被改写**。[ADR-0007](./0007-human-operated-ui-and-record-provenance.md) / [ADR-0024](./0024-provenance-default-by-context.md) 整套 Provenance 的前提是"人说的"与"agent 记的"能分开读。把系统状态拼进用户那段文字，会话记录里就变成**用户说过这句话**；半年后读这段历史的人（通常是另一个 agent）会把它当作用户的关注点。
- **压缩会把它当用户意图带走**。上下文被压缩时，这个块会被当作对话内容总结，甚至演化成"用户似乎关心这 8 条到期项"这种伪意图。
- 系统层带标签的注入能达到同样的"模型必读"，且它可关、可追溯、归属清楚。

**四、失败必须可见。**
三种状态，必须出现在注入里：

| `state`                      | 含义                         |
| ---------------------------- | ---------------------------- |
| `live`                       | 本轮现算成功                 |
| `cache`（带 `age`）          | 取自缓存，且**标明多久以前** |
| `unavailable`（带 `reason`） | 读不到，**原因照写**         |

三条硬规则：

1. **永远注入一块状态**，失败时就是"状态不可得 + 原因 + 修法"。若失败时干脆不注入，那么"扩展坏了"永远只在有人手动想起去查时才暴露，而手动想起正是这套东西要替代的。
2. **绝不阻断对话**：硬超时（1.5s），超时即 `unavailable`，本 turn 照常。
3. **缓存命中必须自报**：把旧状态冒充当前状态，比不注入更坏。

**五、`AGENTS.md` 必须自足，并有一条机械门禁。**
标准 `AGENTS.md` 写全**主回路**（会话开始拉 `brief`；捕获顺序：建决策 → 记清单 → 建预测 → 挂接；结算；事后表达走 `record-reflection`；外加四条硬规矩），而不是"涉及决策时去读某个 skill"。

理由就是加速器存在的同一个理由：**把回路寄存到"模型会去读 skill"上，等于把可用性押在一个未必发生的动作上**；而且有些 harness 根本没有 skill 机制。

两条配套约束，缺一个自足就会腐坏：

- **不复制 skill 的参数细节**：`AGENTS.md` 给"跑哪条命令、什么顺序、什么条件下停"，skill 给追问脚本、参数与例外处理。分工是「不变量 vs 细节」，不是同一段抄两遍。
- **机械门禁**：一条测试要求 `AGENTS.md` 中出现的每条 `npm run --silent agent -- <cmd>` 都真实存在于 `cli/commands.ts`（命令名 + flag）。这是把「文档声明必须可被验证」落到秒级可跑的层面——防的是文档慢慢写出不存在的命令，而那类错误**不会报错**，只会让照着做的人撞墙。

**六、加速器住在仓库外。**
本仓库交付三个暴露面（CLI / Web / skill，见 `AGENTS.md` 第 10 节）。扩展作为独立包分发，本仓库只承认它的存在与边界（本 ADR），**不收录它的实现**——否则"仓库只交付三个面"这句作废，而它的失效面（pi API 变动）也就进了本仓库的维护范围。

## 修正了谁

- **本 ADR 收窄 [ADR-0034](./0034-tracking-is-pull-based.md) 第二点**：「**不提供 pi 扩展、Claude hook、cron 脚本、常驻守护进程。** 交付面就是 CLI + skill（外加给人看的 Web）。任何只在一个运行时里能用的东西，都会把"这套东西能不能用"重新绑回那个运行时」。——收窄为：**不提供承载正确性的 harness 专属物**。判定方法即本 ADR 第一点的验收判据（删掉它回路仍完整）。**cron、常驻进程、外部推送仍然禁止**：它们既不满足判据，也没有"删掉仍完整"的可能（多一个必须活着的进程）。
- **本 ADR 回答 ADR-0034 Considered Options 的这条反对意见**：「**写一个 pi 扩展，在会话开始时自动拉取**：体验最好 → 但它把可用性绑回 pi；使用者换成别的 agent 时这套东西就静默失效，而"失效"不会报错。」——反对意见成立，因此本 ADR 的答法不是"允许它"，而是**把它降到加速器**：回路在别处仍然完整（第一点），失效时要自报（第四点），且它不进本仓库（第六点）。
- **本 ADR 扩展 [ADR-0034](./0034-tracking-is-pull-based.md) 第一点的载体清单**：提醒/状态的载体除 `AGENTS.md` 与 skill 之外，在 pi 里还有"每轮注入"这一条——它是**加速器**，不是基线。基线仍只有 `AGENTS.md` + skill + CLI。

## Considered Options

- **完全不碰 ADR-0034（不做扩展）**：边界最干净 → 但"模型不拉"这个漏洞**承认存在、不修**，而这正是本轮要修的东西。
- **扩展当主通道**（`AGENTS.md` 里不再要求拉取，只靠注入）：体验最好 → 换成其它 harness 时**静默降级**，而文档说不会这样；这正是 ADR-0034 要防的失败形态。
- **把状态拼进用户消息末尾**：最省事、模型必读 → 改写 Provenance、被压缩当用户意图（见第三点）。
- **只在 `session_start` 注入一次**：省 token → 但长会话里状态会变，而"当前状态"过期比没有更坏（人会照着旧数字做决定）。
- **注入为一条独立 message 条目**：用户也看得见，归属清楚 → 同时用会重复占 token；本 ADR 选 guideline 段，`Web` 首页已提供"人也能核对"的那一份。

## Consequences

- **`AGENTS.md`**：重写为自足版（主回路 + 四条硬规矩 + 最小可执行命令序列），不再包含"要怎么数、怎么措辞"这类会过期的细节。
- **门禁测试**：`AGENTS.md` 引用的命令必须在 `cli/commands.ts` 里存在。
- **`docs/uat-pi-agent.md`**：两条路径——**基线**（不装扩展，全部可跑）与**加速器**（装了扩展时多看到什么），后者失败不得影响前者。
- **扩展（仓库外）**：`before_agent_start` 注入 guideline 段；TTL 缓存（同 run 内复用）；1.5s 硬超时；三态自报；不做任何业务判断、不碰数据库、不替代 CLI。
- **成本**：每轮约 50–70 token 的注入，且会让 prompt cache 的复用变差（状态每轮不同）。缓解：只追加不替换 system prompt、块放末尾、同 run 内只生成一次。
- **不做**：cron、常驻守护进程、外部推送通道——它们连"删掉仍完整"都无法成立。
