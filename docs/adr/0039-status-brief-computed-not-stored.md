# 状态简报：现算不落库，唯一生产者 `agent.brief`，两个表面共读同一份

[ADR-0034](./0034-tracking-is-pull-based.md) 让「会话开始时拉一次到期队列」成为跟踪的载体。它解决的是"没人问就不提"，但留下两个问题：

- **一次拉取只够一次对话**。一个长会话里状态会变（结算了一条、新建了一条决策），而队列是开场那一刻的快照。
- **只在 pi 里由模型执行它，等于把"提醒发没发生"押在模型守不守约上**。ADR-0034 明确选了这条路（它的代价写在那里），但代价具体是：状态要经过几次交互才浮出来，而浮不出来时没有任何报错。

本 ADR 定的是**那份状态本身是什么**：内容、单位、分桶、上限、生产者。"它怎么到达会话"由 [ADR-0040](./0040-per-turn-injection-and-accelerator-boundary.md) 管，两篇分开正是因为一个可以只在某个 harness 里实现（到达），另一个必须与 harness 无关（内容）。

**一、简报是现算快照，不落库，唯一生产者是一条 procedure。**
它由 `agent.brief` 每次现算：不建表、不缓存进库、不写"最近一次状态"。理由与 ADR-0020 第三点（完成度是推导值，不落库）完全一致——落库的读数必然过期，而它一旦过期，你会按过期的状态做决定。任何渠道（CLI、Web、每轮注入）读的都是这**同一条 procedure**。

**二、以 Prediction 为计数单位。**
到期分布按预测计，因为**只有 `Prediction` 有 `resolveBy`**。一条决策下的三条预测就是三条，与 `list-due` 同一口径——两个地方各算一遍，才会出现"简报说 8、`list-due` 说 12"，而这种不一致**不会报错**，只会让你不再相信任何一个数字。

**三、分桶按到期时间（`resolveBy`），逾期单列。**

```
逾期 → 一周内 → 一月内 → 一月以上
```

分桶回答的是"这批东西有多陈旧"，而只有到期时间能回答它。**没有预测的决策没有到期日**，因此不进桶，单独一栏——混进桶里会让那一栏出现永远不移动的条目。

**四、明细最多 3 条，只从「逾期 + 一周内」取，按到期由近到远。**
清单未记录**不占明细位**：它在决策创建后就不变了，会永久占据 3 个位里的一个，而一个"永远在那里的明细项"从第三轮起就被无视（ADR-0034 第四点的同一条理由）。它改为独立一行（计数 + 下钻命令）。

**五、计数之外必须给总数、时间分布、以及怎么看到全部。**
只有 3 条而不知道总量，读的人会以为"就这些"。所以每一栏都带总数，每条分桶都带下钻命令。

**六、`seeAlso` 只许指向真实存在的命令。**
下钻命令随返回一起给出（`list-due --bucket …`、`list-decisions --rubric-missing`），并**必须真的存在**。一条指向不存在的命令的提示，比没有提示更坏：它把"我该去看"变成一次失败。

**七、简报不是提醒。**
简报是**状态**（可以每轮都贴，因为它短），提醒是**要求行动**（据 ADR-0034 第四点必须有上限）。两者分开的意义是：状态的容量由"短到不需要被无视"决定，提醒的容量由"不重复到被无视"决定。

内容形状（示意，字段名以实现为准）：

```json
{
  "generatedAt": "2026-10-19T09:00:12Z",
  "due": {
    "overdue": 0,
    "within1w": 8,
    "within1m": 10,
    "beyond1m": 20,
    "unsettled": 38
  },
  "nearest": [{ "title": "…", "dueAt": "2026-10-22", "decisionId": "…" }],
  "rubricNeverRecorded": { "unfrozen": 1, "frozen": 3 },
  "untaggedDecisions": 1,
  "unendorsedForecasts": 2,
  "decisionsWithoutPredictions": 1,
  "seeAlso": {
    "due": "…",
    "rubricMissing": "…",
    "untagged": "…",
    "unendorsed": "…"
  }
}
```

`rubricNeverRecorded` 必须**拆成"还救得回来（未冻结）"与"已披露（已冻结）"**两栏：前者是可执行的动作，后者只是事实（[ADR-0037](./0037-narrative-freeze-and-reflection-channel.md) 定的冻结判据）。混成一个数字，就又把"待办"与"没法定论"混成了一件事——与 ADR-0034 第五点处理 `dangling` 是同一条理由。

## 修正了谁

- **本 ADR 扩展 [ADR-0034](./0034-tracking-is-pull-based.md) 第四点**：「只报**计数**，外加最多 **3 条**最近的到期项；不阻塞对话、不在每次回复里重复。」——**"只报计数"不再够**：还要给总数、时间分布和下钻命令（见第五点）。上限（3 条明细）保留，但适用范围收窄为"明细"，不再是全部输出。
- **本 ADR 为 ADR-0034 第一点增列一个载体**：「提醒只有两个载体，都是中性的：`AGENTS.md` 里一句 / skill 里写触发条件。」——第三个载体是**状态简报**：它可被任何渠道读取（CLI、Web），在 pi 里由 [ADR-0040](./0040-per-turn-injection-and-accelerator-boundary.md) 每轮注入。它仍然**不绑定任何 harness**：内容的生产、读取、下钻全部与 harness 无关。

## Considered Options

- **把六栏塞进 `list-due` 的返回**：少一条命令 → 但 `list-due` 的名字开始说谎（它不再是到期队列），而且 Web 侧仍无对应物，ADR-0023 那条"待议"例外继续欠着。
- **落一张"最近状态"快照表**：读取更快 → 但会过期，且它与"从库里现算"会分叉；两个真相比一个慢。
- **只给计数、不给分布**：最小输出 → 读的人无法判断"这些是不是陈年积压"，而积压正是拉取式要暴露的第一件事。
- **3 条明细里固定留一个位给"清单未记录"**：突出当事人的痛处 → 那一项不会自己消失，会永久占用 1/3 的明细容量，且从第三轮起被无视。
- **按决策计到期分布**（一条决策只要还有未结算预测就算一条，到期取最早那条）：更贴近"决策"这个词 → 但要维护"决策 → 最早到期"的第二个派生，而简报与 `list-due` 会给出两套数字。

## Consequences

- **procedure**：新增 `agent.brief`（放 `agent` router，与 `listDue` / `listUnendorsed` 同处），Web 与 CLI 共读，因此**不进** ADR-0023 的例外表。
- **`agent.listDue` 的"待议"例外维持不变**：简报不替代下钻，Web 仍然没有 `listDue` 的对等物。本 ADR 不假装还了那笔债。
- **下钻**：`list-due --bucket overdue|1w|1m|1m+`、`list-decisions --rubric-missing`；`seeAlso` 由 procedure 生成，不手写。
- **派生口径唯一**：分桶与明细都从与 `listDue` 相同的领域函数取值，禁止第二份实现。
- **测试**：分桶边界（恰好 7 天 / 30 天）、明细上限、明细只取「逾期 + 一周内」、清单未记录不占明细位、`seeAlso` 指向的命令在 `cli/commands.ts` 里存在。
- **Web**：首页渲染同一份简报（数字必须与 agent 看到的一致——这是"可被人类核对"的唯一落点）。
