# 触达接口用"拉取"：待触达项由 pi 会话主动取，本工程不做推送

预留的外部触达接口是**拉取式**的（`T` = ③）：本工程只把"待触达"的内容暴露出来，由 **pi 会话在运行时主动取走**，再交给当事人配置的消息插件（Telegram / 微信等）发送。本工程**不实现推送**，也不维护轮询队列或事件订阅。

为什么不选两种推送形态（① 插件轮询队列、② 事件 / 钩子）：本工程**没有时机去推**。它不是常驻服务——现有定时机制是 Vercel cron（`vercel.json` 里的 `?key=` 路由），本地根本不触发；而 ADR-0005 已经把"何时行动"交给了 pi 调用。让产品侧再维护一套队列或事件总线，等于在 pi 之外另建一套调度，与 ADR-0005 直接冲突。

拉取式还顺带满足 ADR-0013 的兜底要求：**站内通知始终是权威记录**。插件没装、插件失效、当事人不在线，都不影响"这件事需要触达"已经存在于站内——外部通道只是尽力而为的投影。

## Considered Options

- **① 待触达队列（插件轮询）**：需要常驻调度，本地不可运行。
- **② 事件 / 钩子**：在 pi 之外另建一套事件总线。

## Consequences

- 需要一个**只读 + 回报**的接口：pi 会话取待触达项，发送后回报结果（成功 / 失败 / 跳过）。
- "待触达"必须有明确状态机（待发送 / 已发送 / 不再需要），否则重复触达无法避免。
- 具体插件清单与发送契约待当事人提供后补记；**接口形态本身不依赖具体插件**。
- 待触达队列的默认口径：`Notification.deliveryState` 默认 `PENDING`，因此**所有**站内通知（含历史行与既有"可结算提醒"）都在队列里，且不与 `Notification.emailSentAt` 做对账——站内是权威记录，外部通道只是投影，重复触达由插件侧按 `reportDelivery` 的回报收敛。
